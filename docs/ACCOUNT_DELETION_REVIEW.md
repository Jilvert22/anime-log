# アカウント削除の修正

2026-09-07。削除連鎖のSQLは本番へ適用済み。画面・APIの修正はPRで公開する。

## 問題と修正

従来のAPIはテーブルごとのDELETE結果を確認せず、通知設定・通知購読・旧profilesを残していた。実際の本番外部キーにはCASCADEがなく、関連行があるとAuth削除だけ失敗し、視聴記録だけが先に消える可能性があった。Storageの一覧・削除エラーも見逃していた。

- 外部キー7件をON DELETE CASCADEへ変更。Auth削除とDB内の関連データ削除を一括処理する。新規の通報・ブロックも既存のCASCADEで削除される。
- 先に本人のアバターをページ送り・サブフォルダ込みで列挙して削除。列挙、削除、削除後の確認に失敗したらAuth削除へ進まない。
- StorageとAuthを横断するトランザクションはない。Auth削除が失敗すると画像だけ削除済みの場合があることをエラーに明記する。別端末での同時画像アップロードは避けて再試行する。
- 同一オリジン、サーバー側の認証、確認時の本人ID一致を必須とする。古い画面やアカウント切替によって別のアカウントを削除しない。
- リクエスト本文の任意のuserIdを削除対象にしない。サービスキー・SDKの内部エラーをレスポンスに出さない。
- フロントの連打防止、APIインスタンス内の並行実行防止・10分5回の制限。分散レート制限を実装済みとは扱わない。
- 削除成功後のログアウト通信だけが失敗しても、削除失敗とは表示しない。別アカウントへ切替済みならそのアカウントをログアウトさせない。

## 検証

- 変更前に、未認証では削除しないことと、削除先が本人に限定されることを特性テストで固定。
- Vitestで401、別オリジン拒否、確認時ID不一致、100件超とサブフォルダ、画像削除失敗、更新競合、不正なパス、Auth削除失敗を確認。
- `tests/sql/account-deletion.sql` は空の `account_deletion_test` 専用。合成の2ユーザーを使用し、関連テーブルの削除、ロールバック、他方のアカウント保持を確認。
- 本番外部キー名・定義を確認した上で、`20260907000300_account_deletion_cascade.sql` と適用履歴を1トランザクションで反映。既存データの削除は実施していない。
- 実ユーザーのアカウント削除は実行していない。実機での削除実動作には、削除してよいことが明確な検証アカウントを使用する。

## リリース順

DBは先行適用済みで、従来APIの明示的な削除とも互換性がある。新APIはexpectedUserIdを要求するため、更新前の古い画面からの削除は409と再読み込み案内で停止する。APIと画面を同じWebリリースに含める。認証・削除の差分は所有者側Claudeの別セッション監査対象。
