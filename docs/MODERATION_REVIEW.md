# 通報・ブロックの実装と運営手順

更新: 2026-09-07。画面は作業ブランチ上で実装・検証済み。本番DBにはCLIで適用済み。画面公開・Play提出は未実施。

## 利用者の操作

- 公開プロフィールと感想から通報できる。理由と任意の補足（1000文字まで）を保存。送信失敗時は入力を保持し、成功通知を出さない。
- ブロックで双方のフォローを解除。ログイン中のプロフィール、感想、作品一覧、フォローをDB側でも制限。解除はマイページから行い、フォローは自動復元しない。
- ログアウトした人は公開ページを閲覧できる。ブロックは公開情報の完全なアクセス禁止ではない。画面と規約にこの範囲を表示。
- 感想投稿の前に利用規約・禁止事項への明示的な同意を取る。連打での二重送信を防ぎ、投稿後の一覧取得失敗を投稿失敗と誤表示しない。
- 感想の取得、投稿、リアクション、削除は `app/lib/api/reviews.ts` に集約。取得失敗時に再試行できる。既存の作品UUID単位の感想取得範囲は維持。

## DBの制御

正本: `supabase/migrations/20260907000200_moderation.sql`。既存の列型、RLS、公開ビューと特権関数を本番メタデータで照合した。

- `user_blocks`: 自分が設定した一覧のみ読取・削除可能。追加は認証IDを照合するRPCのみ。第三者同士のブロック関係を読む引数はない。
- `content_reports`: 一般ユーザーは直接の読取・追加・変更不可。RPCが対象の可視性を検査し、対象の本文・作者をDBからスナップショット保存。クライアントの申告を証拠として採用しない。
- 保留中の同一通報は1件にまとめ、送信者ごとに24時間で20件まで。同時送信も送信者ロックで直列化。
- `moderation_hidden_targets` と `moderation_actions`: 運営専用。一般ユーザーは非表示の変更・対応履歴の読取不可。非表示の判定結果自体は公開可視性の判定に利用する。
- プロフィール・感想・作品・フォローに既存の公開条件へ追加するRESTRICTIVEポリシー。公開ビューにも明示的に同じフィルタを追加。非表示になった自分の感想は確認・修正できる。
- フォローとブロックは同じユーザーペアのロックを取り、並行操作でフォロー関係が残ることを防ぐ。
- 通報・ブロックのRPCは空のsearch_pathとSECURITY DEFINER。認証ID、対象可視性、入力と上限を内部検証。運営対応RPCはSECURITY INVOKERで一般ユーザーには実行不可、service_roleまたは管理者からのみ実行。
- アカウント削除時には関連する通報・ブロック・対応履歴もCASCADE削除。感想だけを削除した場合は通報スナップショットを保持し、削除済み感想を非表示にする操作は拒否。
- プロフィール・共有ページ・APIはPWAのNetworkOnly対象。閲覧者で変わるレスポンスをWorkboxから再利用しない。OGレスポンスはprivate/no-store。

## 運営の確認と対応

リポジトリルートで、リンク先が `anime-log`（`fskcfnjyyanvzjzsqeju`）であることを確認して使う。Supabase CLIへの管理者ログインが必要。ブラウザにサービスキーを配布しない。

```bash
# 古い順に保留中の通報を最大50件表示
node scripts/moderation.mjs queue

# 表示された通報UUIDを指定して対応（下記の <...> は実値へ置換）
node scripts/moderation.mjs resolve <通報UUID> hide '禁止事項への違反を確認'
node scripts/moderation.mjs resolve <通報UUID> dismiss '違反に該当しないと判断'
node scripts/moderation.mjs resolve <通報UUID> restore '再確認により非表示を解除'
```

`hide` は通報対象の感想、またはユーザーの公開プロフィール・投稿を非表示にする。`dismiss` は当該通報を対応不要として閉じるだけで、既存の非表示を解除しない。復元は `restore` を明示する。複数通報が同じ対象を指す場合、復元は対象自体を再表示するため他の通報も確認する。すべての対応に理由が必要で、履歴を追記する。投稿やアカウントの削除操作ではない。

運営者は定期的にキューを確認し、重大な嫌がらせ・権利侵害・性的搾取などを優先して対象とスナップショットを確認する。通報本文を共有チャンネル等に転載しない。自動審査・担当者への通知・定期実行は未設定であり、このCLIを置くだけで監視している状態にはならない。

- `tests/sql/moderation.sql`: 空のローカルPostgreSQLで匿名／認証ユーザー／運営の権限、双方向ブロック、公開ビュー、リアクション拒否、通報上限・重複、非表示と復元、原文保存、削除連鎖を検証。
- `zsh tests/sql/run-moderation.zsh`: 上記に加え、フォロー先行とブロック先行の2接続同時実行を検証。ローカルPostgreSQLバイナリが必要。ネットワーク接続は使わず一時Unixソケットのみ。終了時に検証DBサーバーを停止。
- Chrome: 390pxで合成の認証・APIだけを用い、通報→ブロック→マイページの一覧→解除を完走。横はみ出しなし、通報ダイアログと一覧を撮影・目視確認。従来のゲスト操作E2E6件も成功。
- 本番SQL適用後、履歴1件、新規4テーブルのRLS、制限ポリシー7件、フォロートリガー、公開ビューを確認。通報はauthenticatedのみ実行可、anon不可。運営RPCはauthenticated不可・service_role可、通報テーブルはauthenticated読取不可。
- 実ユーザーの投稿・フォロー・ブロック・通報を試験のために変更していない。
