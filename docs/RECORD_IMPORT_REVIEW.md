# 記録保全・復元・アカウント統合の確認資料

更新: 2026-09-07
状態: ローカル実装・検証済み。2026-09-07に本番SQLをCLI適用済み。画面コードの本番公開と所有者側Claudeの別セッション監査は未実施。

## 変更の目的

ログアウトすると端末の `animeSeasons` が削除され、保存effectが直前のアカウントの作品をゲスト領域へ書く可能性があった。ログイン切替の読み込み元を追跡し、その保存先と現在の利用者が一致したデータだけを表示・保存するよう変更した。

さらに、第一段階のJSON書き出しを使って記録を戻せるようにした。ファイル・ゲスト記録を入力に、保存先と追加件数・重複件数を確認してから「追加のみ」で取り込む。既存の評価・メモ・進捗を置き換えない。

## 確認するファイル

- `app/hooks/useAuth.ts`: ログアウト時の端末記録削除を廃止。後着の初期セッションで新しい認証状態を上書きしない。
- `app/hooks/useAnimeData.ts`: 読み込み元・取得世代・再読み込み世代で表示と更新を制限。後着レスポンスを破棄。小さいnumber IDをサンプルと決めつけて削除しない。空リストの保存、壊れたJSONの保持、容量不足時の保存エラーと再試行を扱う。
- `app/components/HomeClient.tsx`: 未保存の記録を画面に残し、JSON退避を用意。
- `app/lib/records/importValidation.ts`: バージョン・型・長さ・件数・数値範囲・話数・画像URLを検証。外部の所有者ID、公開レビュー等を取り込まない。
- `app/lib/records/importPlan.ts`: AniList IDを作品同一性に使う。手動作品は元IDと内容をもとにしたキーで区別し、取り込み済みキーを保持。ゲストへは新しいnumber ID／watchlist行IDを割り当てる。
- `app/lib/records/importStorage.ts`: 変更前の控えを先に保存。確認後の編集を拒否。2キー目の書き込み失敗時に元の文字列へ戻す。戻せない場合も控えを保持し書き出しを案内する。
- `app/lib/records/importWorkflow.ts`: 確認した保存先を固定し、保存直前のログイン・記録変更を確認。
- `app/lib/api/recordImport.ts`: DBの読み取りと取り込みRPCを集約。本人再確認と未適用RPCのエラー表示。
- `app/components/tabs/mypage/RecordImportPanel.tsx`: 入力・件数確認・明示取り込み・キャンセル・再確認・復元前の控えの書き出し。

## 本番SQLの適用順（2026-09-07 CLI適用済み）

1. [話数保存](../supabase/migrations/20260907000000_watchlist_progress.sql)
2. [復元・統合](../supabase/migrations/20260907000100_record_import.sql)

[DB運用](db/README.md)に従い、実スキーマと既存RLSを確認してから適用する。両SQLは未適用前提で、同じSQLを再実行する形式ではない。`import_key` はnullableで既存データを変更しない。

取り込み関数は `SECURITY INVOKER`。`auth.uid()` と確認時の所有者を比較し、INSERTの所有者はサーバーで決定する。入力の `id` と `user_id` を採用しない。既存RLS・制約を維持し、`ON CONFLICT DO NOTHING` で既存レコードを更新しない。視聴記録と視聴予定は一つの関数トランザクションで処理する。

RPC未適用時は取り込めない旨を表示し、元ファイル・ゲスト記録を消さない。ブラウザでは2キーをDBのように完全に原子的には更新できないため、事前の控えと失敗時の復旧を用いる。多端末の強いトランザクション保証と同一視しない。

## テスト結果

- 変更前の `useAnimeData` の読み込み・保存・再試行を2件の特性テストで固定してから変更。
- 型検査成功。単体25ファイル・200件成功。検証用コピーで本番形式ビルド・18ページ生成・PWAと通知用Service Worker生成も成功。
- lint: 0エラー・135警告。未使用import削除で1警告減ったため、警告バジェットを136から135へ縮小。
- Chromeの合成データE2E 6件成功。前回4フローに加え、JSON復元・number ID再割当・再実行の重複防止・変更前の控え・不正入力・確認後の競合を確認。390pxで横はみ出しなし。
- 一時ディレクトリの独立PostgreSQLで [SQL試験](../tests/sql/record-import.sql) 成功。本人固定、RLSで他人を隠すこと、匿名実行の禁止、再実行時の重複防止、既存評価の維持、手動作品の区別、途中の制約違反で最初のINSERTも戻ること、25:30の保持を確認。
- ローカルDBは空の最小スキーマに既存資料の型・RLS・一意性を再現したもの。本番の完全な複製ではない。一時DBのサーバーは検証後に停止済み。
- 全検証は本番の `.env*` を読まず、合成データだけで実施。ブラウザの外部通信は遮断。

## 意図的な制限と残件

- JSON形式v1、5MB・5000件まで。CSVからの復元、既存値の上書き、公開レビュー・プロフィール・推しキャラの復元は対象外。
- アカウントへの取り込み成功後も、元の端末記録を自動削除しない。
- 手動作品は取り込みキーで追跡する。以前のファイルにキーがなければ元IDと内容から生成するため、内容の異なる手動記録を同名だけで併合しない。
- 確認後にデータが変わったら再確認する。RPCが保存後に応答を失った場合は、再確認で保存済み分を除外する。
- 取り込み機能は無料。課金・AniList問い合わせ・外部への通知は実行していない。
- 実アカウント切替・Android実機・別セッション監査・PR分割と画面公開が残る。本番SQLとRLS定義の確認は完了。


## 本番適用の追記

所有者の今回のCLI適用依頼に基づき、プロジェクトIDを照合して2件を本番へ適用。詳細は [DB運用記録](db/README.md)。本番確認で作品側の配信情報がjsonbと判明したため修正し、一時PostgreSQLで再検証した。取り込み時に既定の公開フラグを引き継がずfalseを設定する。`public_animes` は公開プロフィールの視聴済み作品を概要表示する既存仕様のため、その点を取り込み画面にも明示した。既存の公開設定・RLSは変更していない。
